# prepaid-revenue-ledger

预付订阅收入逐日封账库（TypeScript + SQLite）。上层直接调用，业务事件与封账结果均持久化在 SQLite 中。只提供三类能力：**批量录入、推进封账、区间导出**。

## 构建与测试

```bash
npm install
npm test
```

只依赖 Node.js（>= 22.5，使用内置 `node:sqlite`）与开发依赖 TypeScript；开发依赖以 `file:vendor/*.tgz` 形式随仓库提供，`npm install` 无需联网。测试含大规模性能用例（30 万项目 / 60 万退款 / 30 年，两种封账模式），整体约 40 秒。

## API

```ts
import { RevenueLedger } from "prepaid-revenue-ledger";

const ledger = new RevenueLedger("ledger.db"); // 打开或创建数据库

// 1) 批量录入已付项目：金额整数分（bigint，1..10^18），日期 UTC 整日，
//    startDate 含、endDate 不含，服务期 1..3650 天
ledger.recordItems([
  { id: "sub-1", amount: 10000n, startDate: "2026-01-01", endDate: "2027-01-01" },
]);

// 2) 批量录入退款：可乱序、可提前登记未来退款；同日多笔按合计处理；
//    生效日不得早于服务起日，每项目退款总额不超过原金额
ledger.recordRefunds([
  { itemId: "sub-1", amount: 2000n, effectiveDate: "2026-06-01" },
]);

// 3) 推进封账截止日（含），只能向前；已封结果不可变
ledger.advanceTo("2026-12-31");

// 4) 导出已封区间：逐日收入、逐日期末递延余额、区间收入合计
const report = ledger.exportRange("2026-01-01", "2026-12-31");
// report.days[i] = { date, revenue, deferred }，report.totalRevenue

ledger.close();
```

约束：生效日不晚于当前封账线的事件禁止补录（调用方保证封账前已补齐）；导出区间必须已封账。违反时抛错。

## 计算规则

对任意日期，令 `C` 为原金额减截至当日已生效退款，`D` 为原服务天数，`k` 为截至当日已经历服务天数（限定 0..D）。应累计确认额 `F`：`k=0` 为 0；`k=D` 为 `C`；其余 `floor(C/D)*k`（日额按分向下取整，尾差归服务最后一天）。当日收入为 `F` 当日与前一日之差（可为负）；期末递延余额 = 已生效预付款 − 已生效退款 − 累计确认额。退款不改变服务期限；服务结束后的退款在生效日直接冲减收入。全部金额以 `bigint` 精确计算。

## 设计要点

- **收入差分数组**：每个项目的逐日收入序列表示为差分事件（区间加日额、退款日点调整、末日尾差），全局聚合到按日差分数组。项目收入事件表是其（金额, 服务期, 退款表）的纯函数，退款变更时撤下旧表、应用新表，因此**与退款录入顺序、批次和封账分段无关**，逐日结果必然一致。
- **封账推进**：游标处维护收入/预付款/退款的差分前缀和，逐日物化到 `daily` 表；已封日期不再受后续录入影响（事件只落在封账线之后）。
- **内存**：项目退款明细只存 SQLite，内存仅保留项目主档与三个差分表；单笔退款处理为 O(该项目退款数)。
- **测试**：小规模用例以独立的逐项目逐日核算（`test/oracle.ts`）为标准，覆盖乱序/同日拆分/尾差/服务结束后全额退款、多模式一致性、恒等式（预付款−退款=累计收入+递延）、非法输入与重开持久化；大规模用例实际执行两种模式并断言 60 秒耗时、512 MiB 峰值 RSS（测试进程以受控 V8 堆上限运行，见 `scripts-run-tests.js`）与 512 MiB 文件上限，比较完整日报并在抽查日期用独立逐笔计算核对。
